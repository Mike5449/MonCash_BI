Ce guide vous emmène de zéro à productif sur le projet en ~45 minutes. Il complète le Guide de Déploiement IT (qui couvre la mise en prod côté ops). Ici on parle architecture, code, patterns et cookbooks.

1. Vue d'ensemble

MonCash BI Portal est un portail interne de reporting pour l'équipe métier MonCash de Digicel Haiti. Il expose sous forme de dashboards les données du data warehouse Databricks (transactions, comptes, KPIs) pour l'audit, le suivi et la conformité (BRH).

1.1 Utilisateurs cibles

  • Analystes métier MonCash — consultation quotidienne des KPIs, exports Excel
  • Équipe conformité — Period Report (BRH), KYC compliance
  • Direction — Snapshots WoW / MoM
  • Auditeurs internes — recherche par MSISDN, historiques transactions

1.2 Fonctionnalités principales

DomainePages
CustomerAccounts, transactions, MTD/Daily stats, churn, KYC info, transaction range
SnapshotsWoW / MoM by type / bank vs wallet / department / channel
B2BBillers + Prefunded + Merchants — accounts, transactions, monthly stats
IMTTransactions, churn (lost receivers), department lookup
OperationsTransactions, e-money ops
Business ToolsFile verification (enrich), Transaction history, Agent OTC, BRH Report, ID Card Scanner

1.3 Non-fonctionnels

  • Portail internal-only (VLAN Digicel, pas d'exposition Internet)
  • Read-only sur Databricks — jamais d'écriture SQL
  • Données J-1 (ETL nocturne), cache 25h + flush 1 AM Haïti
  • HTTPS obligatoire (certificat Digicel Sub-CA)
  • Auth démo actuellement — sera branché sur Azure AD ou l'ASP.NET auth interne

2.2 Flux d'une requête analytique

  1. User ouvre https://ht-moncashreporting.digicelgroup.local/customers/transactions
  2. nginx sert le bundle React (HTML+JS+CSS)
  3. Le composant React monte, appelle un hook useTransactions() (React Query)
  4. Le hook fait GET /api/customers/transactions?start_date=...&end_date=...
  5. nginx strippe /api/ → forward vers backend:8000/customers/transactions
  6. FastAPI vérifie CORS + Host + auth (à venir), puis appelle CustomerService.get_transactions()
  7. Le service appelle CustomerTransactionRepository.get_transactions()
  8. Le repository regarde d'abord Redis (cache), sinon exécute une SQL sur Databricks via DefaultAzureCredential
  9. Résultat stocké en cache Redis (TTL 25h)
  10. JSON renvoyé au navigateur, React Query stocke en cache client, le composant re-render avec les données

7. Backend en détail

7.1 Architecture en couches

Le backend suit une architecture Router → Service → Repository → DB. Chaque couche a une responsabilité claire :

CoucheRôleImport allowed
RouterHTTP endpoints, validation Pydantic, orchestration réponse (JSON, CSV stream, XLSX stream)Services
ServiceLogique métier — orchestration, calculs cross-repositoriesRepositories
RepositoryRequêtes SQL Databricks + cache Redis, transforme Row → dictSQLAlchemy, database.py
DB / SQLDatabricks SQL Warehouse — read-only—
Anti-pattern : jamais faire de SQL directement dans un router ou un service. Toujours passer par un repository. Ça garde la logique DB isolée et testable.

7.4 Auth Databricks database.py

Utilise DefaultAzureCredential (SDK azure-identity) qui tente automatiquement plusieurs sources :

  1. Env vars AZURE_TENANT_ID/AZURE_CLIENT_ID/AZURE_CLIENT_SECRET — le mode utilisé en prod (Service Principal)
  2. Managed Identity — si l'app tournait sur Azure VM
  3. Azure CLI — si az login a été fait localement
  4. Interactive browser fallback

Le token acquis est valide ~1 heure et est caché en RAM avec renewal 5 min avant expiration (thread-safe grâce à un threading.Lock).

L'engine SQLAlchemy utilise un creator custom qui appelle databricks.sql.connect(..., access_token=token) pour chaque connexion pool.

7.6 Service pattern

class BillerService:
    @staticmethod
    def get_accounts(db: Session, limit: int, start_date, end_date) -> List[Dict]:
        repository = BillerRepository(db)
        return repository.get_biller_accounts(limit, start_date, end_date)
Beaucoup de services sont "pass-through" (juste un wrapper autour du repository). C'est OK — la couche existe pour permettre la logique métier future (calculs cross-repositories, transformations complexes).

7.7 Repository pattern

from sqlalchemy import text
import re

_YYYYMMDD = re.compile(r"^\d{8}$")

class BillerRepository:
    def __init__(self, db):
        self.db = db

    def get_biller_accounts(self, limit=100, start_date=None, end_date=None):
        # Anti-injection : valider les entrees
        for d in (start_date, end_date):
            if d and not _YYYYMMDD.match(d):
                raise ValueError(f"Invalid date format {d}")

        # Construction du WHERE dynamique selon les filtres
        date_clause = f"AND to_date(DATE_CODE, 'yyyyMMdd') BETWEEN to_date('{start_date}', 'yyyyMMdd')" \
                      if start_date and end_date else "AND to_date(...) = latest"

        query = f"""
        SELECT DISTINCT
            DATE_CODE,
            IDENTITYMSISDN AS ACCOUNT_ID,
            IDENTITYNAME AS BILLER_NAME,
            ...
        FROM gr_dgc_dwh_prd.ods_dl.mfs_mobile_banking_audit
        WHERE PRODUCTS LIKE '%[Utility Product]%'
          {date_clause}
        LIMIT {limit}
        """
        result = self.db.execute(text(query))
        return [dict(row) for row in result.mappings()]
SQL injection : jamais concatener directement une string user dans une SQL sans validation. Utilisez soit :
  • Bound params SQLAlchemy : text("SELECT * WHERE x = :x").bindparams(x=user_input) — préféré
  • Validation stricte avant f-string : regex, whitelist, cast int()
Les entrées de type date/int passées via FastAPI Query sont déjà castées, mais les strings restent à valider.

8.2 Client API auto-généré

Le dossier src/api/ est auto-généré par openapi-typescript-codegen à partir du schéma OpenAPI du backend. Chaque tag FastAPI (auth, customers, billers…) devient une classe TypeScript avec des méthodes statiques.

// Exemple : src/api/services/BillerService.ts
export class BillerService {
    public static getAccounts(
        limit: number = 100,
        startDate?: string,
        endDate?: string,
    ): CancelablePromise<Array<any>> {
        return __request(OpenAPI, {
            method: 'GET',
            url: '/billers/accounts',
            query: { limit, 'start_date': startDate, 'end_date': endDate },
        })
    }
}
Régénération du client : quand vous modifiez un endpoint backend, il faut regénérer les types côté frontend. Actuellement fait à la main — voir Cookbook §11.3. Un jour on scriptera ça.

8.3 Hooks React Query — hooks/useAnalytics.ts

Un gros fichier qui contient tous les hooks (~40) — un hook par endpoint. Pattern :

// Extrait de useAnalytics.ts
export const useBillerAccounts = (options: {
  limit?: number,
  startDate?: string,
  endDate?: string,
} = {}) => {
  return useQuery({
    queryKey: ["biller-accounts", options],       // cache key
    queryFn: () => BillerService.getAccounts(
      options.limit || 100,
      options.startDate,
      options.endDate,
    ),
  })
}

Pourquoi React Query :

  • Cache client automatique avec dedup — 2 composants qui appellent le même hook = 1 seul HTTP call
  • Refetch au focus, retry auto en cas d'erreur
  • Loading/error states out-of-the-box (isLoading, isFetching, error)
  • refetch() disponible pour refresh manuel

8.5 Composant page-type

Exemple simplifié : une page qui affiche une table de données avec loading state.

import { DashboardLayout } from "../components/Layout/DashboardLayout"
import { useBillerAccounts } from "../hooks/useAnalytics"

export default function BillerAccounts() {
  const [search, setSearch] = useState("")
  const { data: accounts, isLoading, refetch } = useBillerAccounts({ limit: 100 })

  const filtered = useMemo(() => {
    const q = search.trim().toLowerCase()
    if (!q) return accounts ?? []
    return (accounts ?? []).filter(a => a.NAME.toLowerCase().includes(q))
  }, [accounts, search])

  return (
    <DashboardLayout>
      <h1>Billers</h1>
      <input value={search} onChange={e => setSearch(e.target.value)} />
      <table>
        {isLoading ? "Loading..." : filtered.map(a => <tr>...</tr>)}
      </table>
    </DashboardLayout>
  )
}

10.2 Convention de partitionnement

Presque toutes les tables sont partitionnées par DATE_CODE (format yyyyMMdd, string). Toujours filtrer sur DATE_CODE pour éviter de scanner l'historique complet (coût énorme).

Exemple :

-- BON : filtre partition en amont
SELECT ... FROM mfs_transaction_aml
WHERE DATE_CODE BETWEEN '20260701' AND '20260731'

-- MAUVAIS : scan tout l'historique
SELECT ... FROM mfs_transaction_aml
WHERE DEBITPARTYIDENTIFIER = '50937XXXXXXX'

11. Cookbooks — tâches courantes

11.1 Ajouter un nouvel endpoint analytique complet

Cas d'usage : votre PM demande "je veux voir le total des cash-outs par département sur une période". Étapes :

1) Écrire & tester la SQL sur Databricks directement

Ouvrez le SQL Editor Databricks, itérez jusqu'à obtenir la bonne SQL, notez les colonnes de sortie.

2) Créer la méthode dans un repository

# backend/repositories/customer/customer_transaction_repository.py
def get_cashout_by_department(self, start_date: str, end_date: str):
    for d in (start_date, end_date):
        if not _YYYYMMDD.match(d):
            raise ValueError("invalid date")
    query = f"""
    SELECT DEPARTMENT, SUM(ORIGINALAMOUNT) AS TOTAL_VALUE, COUNT(*) AS VOLUME
    FROM hive_metastore.ods_dl.mfs_transaction_aml
    WHERE DATE_CODE BETWEEN '{start_date}' AND '{end_date}'
      AND SERVICENAME = 'Cash Out'
      AND TRANSACTIONSTATUS = 'Completed'
    GROUP BY DEPARTMENT
    ORDER BY TOTAL_VALUE DESC
    """
    result = self.db.execute(text(query))
    return [dict(row) for row in result.mappings()]

3) Ajouter la méthode service (pass-through souvent)

# backend/services/customer/customer_service.py
@staticmethod
def get_cashout_by_department(db, start_date, end_date):
    return CustomerTransactionRepository(db).get_cashout_by_department(start_date, end_date)

4) Exposer l'endpoint dans le router

# backend/routers/customer_router.py
@router.get("/cashout-by-department", summary="Cash-out totals grouped by department")
def get_cashout_by_department(
    start_date: str = Query(..., description="yyyyMMdd"),
    end_date: str = Query(..., description="yyyyMMdd"),
    db: Session = Depends(get_db),
):
    return CustomerService.get_cashout_by_department(db, start_date, end_date)

5) Test rapide dans Swagger

Relancez uvicorn, ouvrez http://localhost:8000/docs, cliquez sur le nouvel endpoint, "Try it out", vérifiez la réponse.

6) Ajouter le hook React

// frontend/src/hooks/useAnalytics.ts — a la fin
export const useCashoutByDepartment = (options: { startDate?: string, endDate?: string } = {}) => {
  return useQuery({
    queryKey: ["cashout-by-department", options],
    enabled: !!options.startDate && !!options.endDate,
    queryFn: () => fetch(
      `/api/customers/cashout-by-department?start_date=${options.startDate}&end_date=${options.endDate}`
    ).then(r => r.json()),
  })
}
Pour utiliser le client auto-généré (préféré), régénérez d'abord : voir §11.3.

7) Créer la page React

Copiez une page existante similaire (ex: BillerAccounts.tsx), renommez, ajustez les colonnes et le hook. Voir §11.2 pour l'entrée sidebar.

12. Cache & performance

12.1 Deux niveaux de cache

NiveauOùTTLInvalidation
Server (Redis)Container bi-redis25hFlush automatique 1 AM Haïti + bouton "Clear cache" UI
Client (React Query)Mémoire navigateurSession (Ctrl+F5 pour reset)Auto-refetch on window focus (défaut)

12.2 Comment le cache Redis est utilisé backend-side

Voir backend/core/cache.py. Le pattern : chaque appel repository check Redis d'abord, sinon exécute la SQL et met en cache.

La clé de cache est dérivée du nom de fonction + hash des arguments. Deux appels avec les mêmes args → 1 seule requête SQL.

12.3 Bypass cache pour debug

Dans l'UI, cliquez le bouton "Clear cache" (icône ⟲ dans le sidebar). Ou en curl :

curl -X POST https://ht-moncashreporting.digicelgroup.local/api/cache/flush

12.4 Pourquoi on fait ça (contexte business)

Databricks SQL warehouse a un coût par requête et un auto-suspend après ~10 min sans activité (cold start ~15-30s au réveil). Le cache 25h :

  • Divise le coût par ~1440 (une exécution par jour vs par requête)
  • Réponse < 100ms au lieu de 2-30s
  • Compatible avec le modèle J-1 (données pas modifiées intra-journée)

12.5 Charts / pages lourdes

Les pages avec charts (Snapshots, Home) peuvent utiliser lazy loading via React.lazy() + Suspense. Pas encore appliqué partout — opportunité d'optimisation.

13. Auth & sécurité

13.1 État actuel — Mode démo

Actuellement frontend/src/services/auth.ts accepte n'importe quel username/password non vide. Aucune vérification serveur. Session en localStorage.

C'est temporaire jusqu'à ce que l'IT décide du serveur d'auth cible (Azure AD ? LDAP ? ASP.NET auth http://hti-dtswebsrv:2020/api/Auth ?).

13.2 Comment activer l'auth réelle

  1. Restaurer le code d'auth ASP.NET dans services/auth.ts (voir historique git avant commit 060a13d)
  2. Ajouter dans nginx.conf un location /auth-api/ qui proxy vers le serveur d'auth
  3. Ajouter VITE_AUTH_API_URL comme build arg dans docker-compose.yml
  4. Test end-to-end

13.3 RBAC backend (préparé, non activé)

backend/models/rbac.py définit Roles + Permissions. scripts/seed_rbac.py peuple la table au startup. Actuellement désactivé dans lifespan — à réactiver quand l'auth réelle sera en place.

13.4 Middleware sécurité en place

  • TrustedHostMiddleware — rejette les requêtes avec Host non whitelisté (config via ALLOWED_HOSTS)
  • CORSMiddleware — restreint les origins (CORS_ORIGINS)
  • SecurityHeadersMiddleware — ajoute HSTS, X-Frame-Options, X-Content-Type-Options, etc.
  • SlowAPIMiddleware — rate limit 200 req/min par IP

13.5 Secrets management

  • Jamais commiter le .env réel (déjà dans .gitignore)
  • Utiliser .env.example comme template
  • Les SECRET_KEY / REFRESH_SECRET_KEY doivent être générés avec openssl rand -hex 64 — jamais réutiliser entre envs
  • Le AZURE_CLIENT_SECRET doit être rotationné selon la politique IT sécurité (1 an typique)

17. FAQ

17.1 Pourquoi Databricks et pas Postgres/MySQL ?

Le data warehouse Digicel Haiti est déjà sur Databricks. Le portail ne fait que consommer (read-only) — il n'y a pas d'écriture métier côté portail (sauf éventuellement la table users pour l'auth future).

17.2 Pourquoi FastAPI et pas Django/Flask ?

Async natif, docs OpenAPI auto (Swagger), typé (Pydantic), écosystème moderne. Pour une API pure c'est le meilleur choix Python actuellement.

17.3 Pourquoi Vite et pas Next.js ?

Pas besoin de SSR (portail interne, pas de SEO). Vite est plus rapide en dev, plus simple à comprendre, et le déploiement en static bundle derrière nginx est trivial.

17.4 Le container backend redémarre en boucle, pourquoi ?

Presque toujours : .env mal configuré (var manquante) ou creds Azure invalides. docker compose logs backend vous dira exactement quelle var manque.

17.5 Le frontend build échoue avec des erreurs TypeScript, pourquoi ?

Le tsconfig est strict — noUnusedLocals: true notamment. Import inutilisé ou variable non lue = build casse. Solution : nettoyer les imports.

17.6 Comment lancer les tests ?

Pas encore de suite de tests automatisés — chantier ouvert. Recommandation quand ça se fera : pytest pour le backend, vitest + testing-library pour le frontend.

17.7 Peut-on ajouter une écriture SQL (INSERT/UPDATE) ?

Techniquement oui, mais **à éviter** — le Service Principal est configuré read-only sur Databricks pour raison de sécurité. Si écriture nécessaire, discutez avec Data Eng — probablement mieux d'avoir un pipeline ETL séparé qui écrit dans une table dédiée.

17.8 Comment ajouter une nouvelle langue (i18n) ?

Pas encore internationalisé. Si besoin : installer react-i18next, créer src/i18n/{en,fr}.json, wrapper les strings du JSX avec t(). Sujet à discuter avant de commencer (impact important).

17.9 Où trouver la référence complète des endpoints ?

http://localhost:8000/docs en local, https://ht-moncashreporting.digicelgroup.local/api/docs en prod. Swagger UI interactive avec "Try it out".
